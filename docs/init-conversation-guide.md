# 项目初始化：说人话交互指南

> **读者**：走 `/auto-nn-init` 的**人**（业务负责人、维护者、旁观 Agent 对话的人）。  
> **用途**：说明初始化对话**应该怎样呈现**——进度清晰、一次只问一件事、选项简单，不把你拖进内部编码。  
> **Agent 执行权威**：[`skills/maintainer/auto-nn-init/SKILL.md`](../skills/maintainer/auto-nn-init/SKILL.md)「用户可见交互协议」。  
> **逐项口径 / 内部编码 / gate 自检**：同目录 [`hard-gate-reference.md`](../skills/maintainer/auto-nn-init/hard-gate-reference.md)（agent-only，**不必**通读）。  
> **HARD-GATE 逐项对照（含编码）**：`template-migration-hard-gate-guide.md`。  
> **英文用户**：Agent 跟你的语言走（进度抬头 / A/B/C 用英文）；逐项口径内部仍是中文编码，不会把内部表摊给你。

---

## 1. 为什么要「说人话」

初始化要在**改任何代码之前**，把任务、数据、训练、评估、机器占用等口径对齐。后台需要一套稳定的内部编码（便于写 `.auto-nn/migration-summary.md`、跑 verify），但**对话里不应把这套编码甩给用户**。

常见坏体验：

| 坏体验 | 为什么有问题 |
|--------|--------------|
| 一条消息里连问 H1+H2+H3，结尾「请一并回复」 | 用户不知道先答哪个；漏答后 Agent 又重复问 |
| 没有「第 3 / 共 27 步」 | 不知道还要确认多久 |
| 满屏内部代号（训内打哪条路 / 合同汇总表 / 内部动作） | 理解成本像在读维护文档，不像在确认业务 |
| 阶段 0 贴整份 A–F 盘点表 | 信息过载；真正要确认的反而被淹没 |
| 把「签字确认口径」说成「迁完了」 | 签字 ≠ 完成；完成还要 verify + smoke |

**目标**：你像和产品经理对齐需求一样对话——**一次一个主题、看得懂进度、A/B/C 就能答**。

## 2. 三层分工（谁读什么）

| 层 | 文件 | 给谁 | 写什么 |
|----|------|------|--------|
| **人话剧本** | `SKILL.md` | Agent | 对用户怎么说：进度抬头、四段式问句（含「这一步在定什么」）、禁止暴露的内部码 |
| **引擎参考** | `hard-gate-reference.md` | Agent | 内部编码、逐项问话全文、矛盾检查、F1 模板（**不对用户展示**） |
| **本文** | `init-conversation-guide.md` | **人** | 你会看到什么、好/坏示例、主题顺序与步数 |

业务仓**不复制** `docs/`；若你在业务仓里跑 init，对话规范仍由全局技能 SKILL 约束 Agent。

## 3. 你会经历什么（五阶段，人话版）

```mermaid
flowchart LR
  P0[0 先读懂项目] --> P1[1 逐项确认口径]
  P1 --> P2[2 实现代码]
  P2 --> P3[3 治理与卫生]
  P3 --> P4[4 验收]
  P4 --> Done[迁后日常实验]
```

| 阶段 | 对你意味着什么 | 会不会改代码 |
|------|----------------|--------------|
| **0 分析** | Agent 读旧项目或模板；给你 **3～5 条**「我对项目的理解」 | 否（只读） |
| **1 逐项确认** | 按主题一个一个问；最后 **单独一轮**「口径汇总，请签字」 | 否（只读） |

**并联（v1 极简）**：默认仍一题一轮；仅迁入入口 A 在「旧资产清理」段，经验文档取舍与 README 边界两题可同屏点选（各独立 A/B/C，可选手动「分开问」）。真源 `docs/init/init-interaction-policy.yaml`，经 `/auto-nn-update` 下发。
| **2–4 实现与验收** | 在新目录里改 contract/workspace、同步治理、跑 verify + smoke | 是 |

**两条入口**

| 入口 | 含义 | 阶段 1 大约几步 |
|------|------|-----------------|
| **A 迁入已有项目** | 旧仓只读；**新建**目标目录再移植 | **27** 步（另加「对齐理解」准备步 + 最后签字） |
| **B 从零立项** | 无旧代码，直接 greenfield | **24** 步（无「旧资产清理」段） |

**先交答卷（可选）**：已经想好的答案可以一次交进来，不必一题一题从零点。形式不限：标准 YAML、md/txt、或聊天里一段笔记。Agent 先填成标准表并给你看覆盖表（写清了的跳过点选，猜的和没写的照问），最后仍要你确认总表。立项结束后会多一份 `.auto-nn/init-answers.yaml`，下次同类立项可以直接扔回去。YAML 示例：`python3 scripts/init_answers.py template --workflow build`。完整表只签字须 27/24 问都写清且没有「我猜的」。

**铁律（对你最重要）**

- **签字只是锁定口径**，不代表迁移完成。
- **完成** = 跑验收脚本 exit 0 **且** 短训脚本通过。
- 签字前 Agent **不应**改你的业务代码。

## 4. 进度抬头：始终知道「第几步 / 共几步」

阶段 1 的**每一条**用户可见消息，开头应有一行人话主题 + 进度，例如：

```text
【信息权限 · 第 3 / 共 27 步】
```

「对齐理解」在正式计数之前，可写：

```text
【对齐理解 · 开始前确认】
```

全部步数确认后，**另起一条**做汇总签字（不算进步数里）：

```text
【口径汇总 · 请最终确认】
```

### 4.1 主题顺序与步数（入口 A，27 步）

| 步 | 人话主题（Agent 对你怎么说） |
|----|------------------------------|
| 准备 | **对齐理解** — 任务 / 数据 / 怎么打分 / 风险（不计入 27） |
| 1–2 | **场景与数据** — 有哪些实验场景、数据怎么划分 |
| 3–5 | **信息权限** — 训练能用哪些材料（哪些只评）、官方分必须走哪条路、还有没有别的信息规矩 |
| 6–7 | **场景与数据（续）** — 训内数据处理、复现用哪套数据 |
| 8–10 | **旧资产清理** — 旧成绩记录与实验目录、经验文档、旧 README 里的硬约束（仅入口 A） |
| 11–12 | **训练方式** — 哪些 loss/约束不能动、训练循环怎么跑 |
| 13 | **主指标** — 主/辅指标叫什么 |
| 14–15 | **实验目标** — 这轮主要追什么（追指标 / 新方法+指标 / 摸底）；主指标目标值或摸底护栏（**须在场景探索方案之前**） |
| 16–23 | **评估与成绩记录（续）** — 指标分级、官方测试、训内评估、成绩列、**场景探索方案**、运行参数列、模型存档、怎么算「更好」等 |
| 24–27 | **运行设置** — 单次训练最长多久、用哪些 GPU、起步尺子、随机种子 |
| 末 | **口径汇总签字**（不计入 27） |

### 4.2 入口 B（24 步）

与上表相同，但**没有**「旧资产清理」三步（原 8–10）；步号整体 **−3**：`对齐理解 → 场景与数据(2) → 信息权限(3) → 场景与数据续(2) → 训练(2) → 主指标(1) → 实验目标(2) → 评估续(8) → 运行(4) → 签字`。

### 4.3 逐题怎么答（迁入 27 / 立项 24）

对照表写在仓库首页，打开就能看：

- 中文：[README-zh 附录](../README-zh.md#init-qa)
- English: [README appendix](../README.md#init-qa)

对话里仍是一题一轮、A/B/C 点选。迁入 27 步；从零立项没有「旧资产」三步。Agent 会按你的代码给建议，**迁入时优先跟源项目**，不要为了「更规范」改划分或打分方式。

### 4.3 Per-question answers (English)

The per-question table lives on the repository README (same links as above). **Migrate** = 27 steps; **greenfield** has no “legacy assets” trio. When connecting an existing repo, follow the source instead of “cleaner textbook” splits.

## 5. 默认问句格式：四段式 + A/B/C

每个问题尽量只占**一件事**，结构固定为四段（**第 0 段 mandatory**）：

0. **这一步在定什么** — 1 句白话或程序员类比（不用查文档也能懂在定啥）
1. **我看到的现状** — 3～5 条要点（从代码/README 归纳，少术语）
2. **我的建议** — 一句推荐 + 必要时一句「为什么」
3. **你怎么选** — 只给字母选项，或留空让你填

> **迁入时「推荐」= 尽量对齐源项目**（划分、训内是否看 test 等可核对设定）。更公平/更规范的改法只作备选，不要标成推荐。从零立项才可默认推教科书式划分。真源：`skills/maintainer/auto-nn-init/SKILL.md` + `hard-gate-reference.md`「迁入推荐铁律」。

```text
【训练方式 · 第 11 / 共 27 步】

这一步在定什么
- 不是问「现在用哪个 loss」。
- 是定：以后自动改实验时，训练目标的底线与松紧（什么碰不得、什么可以动）。

我看到的现状
- 源里常见用 H1 训、Lp 评；还有加权、自适应权重一类技巧

我的建议
- 必须留着：打分仍用 Lp / H1，别换成 MSE
- 可以换：训练主损失在 Lp、H1、两者加权之间切换
- 可以加：在主损失上再加辅助项（没有就写暂无）
- 只能拧旋钮：d、p、reduction 等
- 可选技巧：自适应加权开/关均可

你怎么选
A) 就按上面的边界来（推荐）
B) 我想更严：______
C) 我想更松 / 自己改：______
```

> 上例是「训练里什么能动」专用样板。Agent **不会**对你念「五档/分层表」——那是内部记口径用的。

```text
【训练方式 · 第 12 / 共 27 步】（下一问：调用链，勿与上步混）

这一步在定什么
- 训练循环怎么转，以及一圈训完后何时打分。

我看到的现状
- …

我的建议
- …

你怎么选
A) 按我的建议来（推荐）
B) 保持现状不变
C) 我来改：______
```

你可以直接回 `A`、`B`、`C`，或用自然语言说明；**不需要**回数字编号或背内部代号。

### 5.1 给普通程序员：每一步像在定什么

| 阶段 1 主题（节选） | 像在做啥（一步白） |
|---------------------|-------------------|
| 场景清单 | 列几种「官方实验设定」+ 各自起跑配置 |
| 数据划分 | train/val/test 怎么分；终评用哪套数据 |
| 训练许用材料 | 训练能碰哪些数据、哪些只在打分时打开（像保险柜钥匙只在验收时用）。代码里可以预留「不用的钥匙」，真去开柜才算犯规 |
| 官方打分通道 | 官方分只能走哪条路算（像接口只准走网关、不许绕直连） |
| 其他信息规矩 | 还有没有别的信息不许乱流（机器只管训练 batch 键，其余人审） |
| 训练里什么能动 | **不是**问现在用哪个 loss；**是**定自动改实验时训练目标的底线与松紧 |
| 旧成绩与产物 | 旧 CI artifact / 实验目录要不要迁 |
| 调用链 | 训练 for-loop 怎么转、何时 eval |
| 主/辅指标 | KPI 主分 + 辅助 metric |
| 实验目标 | SLO：主分要到多少、达标即停 |
| 场景探索方案 | 每轮允许改啥、多场景怎么轮换比最好 |
| 怎么算更好 | promote 规则：什么算「这次更好」 |
| GPU 与并行 | 用哪些卡、最多几路 job |
| 口径汇总签字 | 需求评审签字——**不是**迁完 |

完整 27/24 步「问什么、怎么答」见仓库首页 [README-zh 附录](../README-zh.md#init-qa) / [README appendix](../README.md#init-qa)。Agent 内部一步白见 [`SKILL.md` §2.1](../skills/maintainer/auto-nn-init/SKILL.md)。

## 6. 三个特殊节点

### 6.1 阶段 0 — 先读懂，别轰炸

Agent 读完项目后，对你只讲 **3～5 条**人话总结，例如：

- 这是什么任务（监督 / RL / 物理仿真）
- 数据从哪来、官方 test 是什么
- 现在怎么打分、怎么留「最好的一次」
- 1～2 个需要注意的风险

完整的逐项盘点表由 Agent **写入** `.auto-nn/migration-summary.md` 存档，**不要**整段贴在对话里。
（对照分析的只读报告可以整段给出，那是分析材料，不是确认问卷。）

### 6.2 对齐理解 — 进入「第 1 步」之前

```text
【对齐理解】这是我对项目的理解，对吗？
- 任务：…
- 数据：…
- 怎么打分 / 留最好成绩：…
- 我注意到的 1～2 个风险：…

A) 没问题，开始逐项确认
B) 有偏差，我帮你改：______
```

你确认后，Agent 才进入「第 1 / 共 27 步」。  
入口 A 时，Agent 还应在此时前后给出 **1～3 个建议的新目录名**，等你拍板后再 `new-project.sh`（禁止在旧目录原地改）。

### 6.3 口径汇总签字 — 全部步数走完后单独一轮

- 用**人话行名**汇总你已确认过的决定（不必出现内部 slug）。
- 必须说明：**这一步只是锁定口径，不代表迁移完成**；确认后 Agent 才开始改代码。
- Agent 内部会把带编码的完整合同与矛盾检查写入 `.auto-nn/migration-summary.md`——**那是归档，不是让你逐行审编码表**（场景清单的权威在 README 的场景段）。

### 6.4 实验目标 — 主指标之后、场景探索方案之前（两轮）

**为什么放这里**：探索方案（下一步 E6）和**实验目标**紧密相关——须先定「追数 / 方法+数 / 摸底」，再定「每轮改什么、场景怎么排期」。

**第 11 步：这轮主要干什么**

```text
【实验目标 · 第 14 / 共 27 步】
- 我看到的现状：主指标是「准确率」（上一步已确认）；模板默认是「先把主指标做上去」。
- 我的建议：多数项目先追指标；若要逼 Agent 走出现成库，选「新方法+指标」。
- 你怎么选：
  A) 先把主指标做上去（推荐）
  B) 既要指标，也要更深一点的方法
  C) 先摸清方法空间（指标别崩就行）
```

**第 12 步：主指标要到多少**（若你选了 C「摸底」，会问是否设护栏，默认不设数值主目标）

**简单分类（MNIST / FMNIST / CIFAR-10 等，主指标为准确率）**

```text
【实验目标 · 第 15 / 共 27 步】
- 这一步在定：主指标最终要到多少算达标即停（不是后面「单次算不算进步」）。
- 我看到的现状：主指标是「测试集准确率」；达标即停，目前还没设目标值。
- 我的建议：按任务给几档；拿不准就选「暂不设」。不用先跑实验。
  · 0.95 较易，适合先验证流水线
  · 0.99 难，可能长期跑满 N 轮
- 你怎么选：
  A) 目标 0.95
  B) 目标 0.98
  C) 目标 0.99
  D) 暂不设（不确定时推荐）
```

**损失 / 误差 / RL 回报等**：默认推「暂不设」，有明确目标再填数（见 SKILL §5.1.2）。

### 6.5 场景探索方案 — 实验目标之后（E6）

**这不是再问「要不要探索」**——**实验目标**已在第 11–12 步定过。本步只定：**每轮允许改什么、一次专注几个场景、最好成绩怎么分开比**。

```text
【场景探索方案 · 第 20 / 共 27 步】
- 我看到的现状：
  - 你已选：先把主指标做上去
  - 已有两个场景：reference（19 个经典模型对照库）、automatic（Agent 自己提新方法）
  - 本步只定轮转规则，不是绑死「探索只能用 19 个方法」
- 我的建议：每轮只换模型架构；学习率等超参先锁起跑线；一次专注一个场景；两个场景的最好成绩分开比
- 你怎么选：
  A) 按建议来（推荐）
  B) 每轮允许多样东西一起改
  C) 固定单一架构，不换模型
  D) 我来说：______
```

与「起手探索档」（第 23 步运行设置里问）**不是一回事**：起手档管**在同一「每轮改什么」之下**先动学习率还是结构；须在目标与场景方案都定完之后才问。

### 6.6 怎么算更好 — E9（checkpoint 之后）

**与第 12 步分开**：第 12 步是「最终达标停」；本步是「单次实验算不算进步、要留下来」。

**FMNIST / 分类准确率示例**

```text
【怎么算更好 · 第 23 / 共 27 步】
- 这一步在定：单次实验比历史最好好多少才算更好、要留下来。
- 我看到的现状：主指标是「测试集准确率」，越大越好。
- 我的建议：比例类准确率，不用先跑实验。推荐涨 0.1% 就算更好；涨 0.5% 是旧默认，高平台期可能很多轮都留不下。
- 你怎么选：
  A) 涨 0.1%（推荐）
  B) 涨 0.2%
  C) 涨 0.5%
  D) 自定义
```

选完后 Agent 会写入配置；以后觉得太松/太严可改 `nn-config.yaml` 里 keep 相关项。

## 7. 一轮只问一件事（硬规则）

| 规则 | 说明 |
|------|------|
| 一条消息 ≤ 1 个主题 | 禁止同条出现多个主题标题或「H1/H2/H3 请一并回复」 |
| 用户批量回答也不合并 | 你若一次答了很多，Agent 仍应**逐个补问**未确认项 |
| 签字表必须单独一轮 | 27/24 步未齐前，不得预发完整汇总表 |
| 答案清单不改题序 | 你先交的答卷只让对应题「不弹卡片」；顺序、记录、签字都照旧，写错的题会先报错再照常问 |
| 发出前自检 | 这条消息里有没有内部编码、有没有超过一个主题、有没有「这一步在定什么」？有则改人话或拆到下一轮 |

[`SKILL.md` §一轮一问 / 4 问自检](../skills/maintainer/auto-nn-init/SKILL.md) 对 Agent 强制执行上述外壳与发出前 4 问自检。

## 8. 好示例 vs 坏示例

### 8.1 进度与主题

**好**

**案例 3：训内/台账术语泄漏**（CIFAR 类 init 常见）


**泄漏**：`Run Context` / `finalize_round` / `journal` / `KEEP` / `improve_mode` / `primary_delta` / `ledger` / `scenario_id` — 普通程序员无法在不读 PROTOCOL 的情况下选型。

**改后**：

```text
【训内评估 · 第 18 / 共 27 步】

这一步在定什么
- 训练过程中要不要打分、多久打一次（和训结束后的「官方终评」不是一回事）。

我看到的现状
- 每圈 epoch 结束会跑一次验证集，指标和终评用的是同一套准确率算法
- 历史最好成绩只看训结束后的官方测试，不看训内曲线

我的建议
- 训内每圈都评；留最好成绩仍只看终评（和模板默认一致）

你怎么选
A) 按建议来（推荐）
B) 训中不评，只在训末评一次
C) 我来说：______
```
