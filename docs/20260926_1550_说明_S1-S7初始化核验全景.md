# 说明：S1–S7 初始化核验全景（是什么 / 什么关系 / 结果如何）

- **日期**：2026-09-26
- **状态**：✅ S1–S7 全部完成并收口——15 项发现全闭环，复测三件套两轮全绿零回归，真 B16 冒烟 PASS
- **本文定位**：一份自足的「S1–S7 到底指什么」介绍。细节出处见 §6 文档地图。

## 0. 一句话

S1–S7 是 STEER 框架「答卷立项实验仓」链路的一组**核验编号**：**三个建仓入口（S1/S2/S3）× 三个起步尺叶子（S4/S5/S7）+ 一条手工横切边界（S6）**——考的是「任意来路 × 任意起步声明」组合下，立项产物和首轮自动行为都正确。

⚠️ **撞名提醒**：auto-nn-factory spec 里另有一套「六段流水 S1–S6」（问需求 → 造数据 → 验收 → 渲染答卷 → init 出仓 → 迭代接管），那是**服务编排阶段编号**，与本文的核验编号 **S1–S7 毫无关系**，只是恰好都叫 S。两套编号所在文档不同：六段流水在 factory spec，核验编号在 STEER（steer/docs/ 与飞书词条页）。

## 1. 每个编号是什么

### 1.1 建仓三入口 S1 / S2 / S3（只决定「仓怎么来」）

| # | 名称 | 命令形态 | 一句话 |
|---|---|---|---|
| S1 | 从数据新建 | `--workflow build` | 只有数据 + full 答卷，无家底白手起家——考「从零建」 |
| S2 | 模板迁移 | `--workflow migrate` | 以参考仓为模板整体搬家——考「保真」；S2b = 同命令复现跑，归一化后应逐字一致 |
| S3 | 答卷优先改造 | `migrate + 改造答卷` | 模板 8 波束 vs 答卷 16 波束打架时听答卷的——考「改造」 |

### 1.2 起步尺三叶子 S4 / S5 / S7（只决定「首轮自动发什么」）

分叉点 = 立项尾部 write_intent 读答卷 O3 lock（「起步尺子」声明）：

- **S4 plain 落位**（答卷声明 `O3.PLAIN=`）：首轮自动发 plain FIRST-ROUND 提示（带 plain_recipe），非AI规则尺按答卷落、不抄模板实测值；**贯穿维度，不是第四条建仓路径**——S1–S3 每场景验收必查。
- **S5 reference 落位**（答卷声明 `O3.REFERENCE=`）：首轮自动发立尺提示，带来源校准硬门原文（check-source-cal 过线才可贴公开对照尺，auto 不放松）；修前 reference-only 答卷会因 intent 缺省**误推 plain**，已修（d2b8832）。
- **S7 无声明缺省**（两者都没声明）：按原有逻辑——缺省照推 plain + skipped 标记留痕；reference 只走满 10 轮被动兜底；手工技能随时可用。与 S5 零耦合零回归。

### 1.3 横切边界 S6（不在判定树上）

立项自动只管**首轮「定什么」**（plain 自动跑；reference 自动发提示但硬门不自动放行）；运行期的立尺/换尺（--replace）/补尺/校准归**手工技能** auto-nn-plain / auto-nn-reference——两层互补、保留不删。已做过再手动触发会被 stamp_tag 拒绝（每场景每把尺最多一行；当前最好不能贴成 reference 自比；plain 行不能改贴 reference）。

### 1.4 容易误会的两点

- **S4 不是第四条建仓路径**：它是贯穿 S1–S3 的核验维度。
- **S2b / S3b 不是新场景**：S2/S3 的同命令复现对照跑，验证「再来一次结果一样」。

## 2. 关系：判定树（入口 × 叶子正交）

```
建仓入口（S1/S2/S3，只决定仓怎么来）
  S1 --workflow build    从数据新建（无家底）
  S2 --workflow migrate  整体迁移参考仓（保真）
  S3 --workflow migrate+答卷  迁移并按答卷改造
        |  三条入口汇入同一条 init 尾部：
        v
  resolved lock -> render_init_blocks -> write_intent -> 首轮 render
        |  分叉点 = write_intent 读 O3 lock（起步尺声明）
        v
  +- 有 O3.PLAIN=      -> S4：start_runs=plain，首轮发 plain FIRST-ROUND（带 plain_recipe）
  +- 有 O3.REFERENCE=  -> S5：start_runs=reference 或 plain+reference，
  |                         首轮发 reference FIRST-ROUND（带校准硬门原文）
  +- 两者都没有        -> S7：缺省照推 plain + skipped 留痕；
                            reference 只走满 10 轮被动兜底
S6（横切边界，不在判定树上）：运行期立尺/换尺/补尺 = 手工技能；
  重复贴 stamp_tag 直接拒绝（--replace 才换）
```

**正交结论**：任意入口 × 任意叶子组合都走同一条 init 尾部（resolved lock → render_init_blocks → write_intent → 首轮 render）——入口只决定仓怎么来，叶子只决定首轮发什么。

**为什么会有 S5**：修前 write_intent 不认 `O3.REFERENCE=`，reference-only 答卷掉进「无声明」分支且缺省误推 plain——S5 分支补上（d2b8832）后三片叶子才完整覆盖判定树。

## 说人话

给新同学的一句话版本：用 STEER 框架立项实验仓时，仓库的「来路」有三种——从零建（S1）、照样板搬（S2）、照样板改（S3）；仓库起步时那把「不用 AI 的尺子」按答卷声明自动落位——声明了规则尺就自动跑（S4）、声明了公开对照尺就自动发立尺提示但要过校准关（S5）、什么都没写就按老规矩来（S7）；而运行中想换尺补尺，用的是手工技能（S6），重复贴会被拦。整套行为我们用 39 项全量测试 + 19 项故意使坏测试 + 一遍真数据实跑反复验过，全绿。另外注意：factory 服务流程里的 S1–S6 是另一套编号，别混。

## 缩略语

- **STEER**：本仓（steer/）答卷立项实验仓的框架/模板体系
- **S1–S7**：初始化核验编号——S1 从数据新建 / S2 模板迁移 / S3 答卷优先改造 / S4 plain 落位（贯穿）/ S5 reference 落位 / S6 手工技能横切边界 / S7 无声明缺省；S2b/S3b = S2/S3 的同命令复现对照跑
- **factory 六段流水 S1–S6**：auto-nn-factory spec 的服务编排阶段编号（问需求→造数据→验收→渲染答卷→init 出仓→迭代接管），**与 S1–S7 无关，仅撞名**
- **答卷（answers）**：立项问答卡 yaml，口径的唯一来源
- **O3 lock**：答卷「起步尺子」题冻结出的结论行（O3.PLAIN= / O3.REFERENCE=）
- **plain**：非AI朴素基线（规则尺：如被测波束子集内取 RSRP 最大）
- **reference**：公开对照尺（论文/参考仓成绩，贴前须过来源校准硬门）
- **write_intent / intent**：立项尾部把起步尺声明写成机读意图文件（首轮自动执行的依据）
- **FIRST-ROUND**：首轮注入 agent 的提示段
- **check-source-cal / ledger_midpoint**：对照尺来源校准；不过线时落中点占位
- **stamp_tag**：贴尺落台账的动作（每场景每把尺最多一行，重复贴拒绝，--replace 才换）
- **doctor**：nn-doctor.sh 项目体检（PASS/WARN/FAIL）
- **暴露集 / Set-B**：UE 可测量/可选的候选波束子集（N 个 / 全体 M 个）
- **RSRP**：Reference Signal Received Power（参考信号接收功率）
- **UE**：User Equipment（用户设备）
